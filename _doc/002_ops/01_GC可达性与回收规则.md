# GC 可达性与回收规则（以代码为准）

> 任务：TASK-20261012-027 · 范围：z-graph 版本链 GC
> **本文每一条都能在代码里逐行对上**，出处写在每节末尾。
> 改代码先改本文；本文与代码不一致时，**以代码为准并立刻修本文**。

## 0. 一句话

`garbageCollect(String... keepBranches)` 回收「**不被任何保留分支引用**」的 commit，
并把**指向不可达 commit 的分支 ref 一并剪掉**。
被保留分支引用的 commit（分支头 + 它的全部祖先）**不可回收**。

## 1. 入口

| 层 | 位置 | 说明 |
|---|---|---|
| 引擎 | `z-graph-core/.../core/GraphVersionStore.java` → `garbageCollect(String... keepBranches)` | 真正的回收逻辑（同步方法） |
| 运维封装 | `z-graph-core/.../core/GraphMaintenanceService.java` → `collectGarbage(String...)` | 加计数/时间戳/最后一错，失败照抛 |
| HTTP | `z-graph-bolt-server/.../bolt/GraphControlServer.java` → `POST /maintenance/gc?keep=main,feature` | z-schedule 定时打这个端点（Bearer Token 必填） |

## 2. keep 集合（保留哪些分支）

- `keepBranches` 为 `null` 或**空数组** ⇒ keep = **当前全部分支**（`listBranches()`）。
- 否则 keep = **显式给出的分支名**。
  - 名字不合法（不匹配 `[A-Za-z0-9._/-]+`）⇒ `IllegalArgumentException`。
  - 分支不存在 ⇒ `UnknownReferenceException`（**直接失败，不静默跳过**）。
- ⚠️ **显式 keep 时，未列出的分支不是"这轮先不收"，而是被剪掉**：它们的 ref 指向的 commit
  不在可达集 ⇒ ref 被删、分支消失、其历史被回收。**这是本 API 最容易误删的一条**。
  生产上要么不传 `keep`（= 全部分支受保护），要么把要留的分支**一个不漏**地列全。

> 出处：`GraphVersionStore.garbageCollect` 第 839–853 行。

## 3. 可达集怎么算

对 keep 里**每个**分支的 head，取两部分的并集：

1. `AncestryIndex.lineageToRoot(head)` —— 沿**第一父**链到根（自身在前）。
2. `AncestryIndex.closureOf(head)` —— 沿**全部** parents 递归的 commitSeq 祖先闭包（**含 head 自身**）。

`closureOf` 沿全部 parents 递归 ⇒ **merge 双父天然覆盖**：merge commit 的第二父及其祖先都在闭包里。

> 出处：`GraphVersionStore.garbageCollect` 第 842–853 行；
> `AncestryIndex.closureOf` / `AncestryIndex.lineageToRoot`。

## 4. 回收动作（回收了什么 / 没回收什么）

**回收（不在可达集里的 commit）**：

- 删掉 commit object 文件；
- 从 `commitIdBySeq` / `commitHandles` 索引里摘掉。

**剪 ref**：所有分支 ref 中，指向的 commit **不在**可达集 ⇒ 该 ref 被删（分支消失）。

**压实（仅当确实回收了东西时）** `compactStorage()`：

- 把**仍可达**的 commit 的 delta 按 commitSeq 升序重放进新的 `store/` 目录，原子换名替换旧目录；
- 不可达的版本记录与墓碑随之消失（`versionRecordCount` / `payloadBytes` 回落到可达历史的真实规模）；
- **commit id / commitSeq / refs 不变** ⇒ 可达性判定不受影响；
- 之后 `ancestry.invalidateAll()`：闭包缓存整表作废（不可达 commit 已删，闭包基座变了）；
- 换名窗口崩溃由构造器 `recoverCompactionCrash` 收尾（`store/` 完整 / `retired`+`compacting` 同在 / 只有 `retired`）。

**返回值**：被回收的 commit 数量。

> 出处：`GraphVersionStore.garbageCollect` 第 854–881 行；`compactStorage` 第 893–919 行；
> `recoverCompactionCrash` 第 935–955 行。

## 5. 不会发生什么（安全性）

- **保留分支的 head 不会被回收**：闭包含自身。
- **保留分支的全部祖先不会被回收**：这些历史仍可按 commit id 打开（`checkout(commitId)` 正常）。
- **被合并（merge）的分支历史不会被回收**：merge commit 的第二父进闭包。
- **不传 keep ⇒ 全部分支受保护** ⇒ 只回收"无任何分支指向"的孤儿 commit。
- 压实只重放**仍可达** commit 的 delta ⇒ 可达历史的内容与顺序不变。

## 6. 别混用的几个口径

| 口径 | 怎么算 | 与 GC 可达集的关系 |
|---|---|---|
| `reachableCommitCount()` | 按**全部** ref 的 `closureOf` 统计 | 显式 keep 时**不等于** GC 的可达集（GC 只算 keep 集合） |
| `/meta/stats` 的 `commitCount` | 仓库里全部 commit 数（含不可达） | 回收前后对比看它有没有掉 |
| `/meta/metrics` 的 `maintenance.gcCollectedCommits` | 累计回收数 | 失败/成功都记 |

## 7. 运维口径

- **定时**：由 z-schedule 触发 `POST /maintenance/gc`（handler 见
  `z-schedule-core/.../core/handler/GraphMaintenanceHandler.java`）。
- **上线纪律**：GC 与备份策略上线前先在**测试 data-dir** 演练；**生产目录首轮只观察不自动跑**。
- **数据目录**：用规范键 `z.base.graph.data-dir`（兼容别名 `z.graph.data-dir`）——
  由 TASK-20261012-026 定稿，不要再发明新键。
- **指标**：`GET /meta/metrics` → `maintenance.{gcRuns,gcCollectedCommits,gcFailures,
  snapshotExports,snapshotFailures,lastGcAtMillis,lastSnapshotAtMillis,lastError}`。
- **响应头（给调度侧用）**：`POST /maintenance/gc` 回 `X-Gc-Collected` /
  `X-Gc-Commits-Before` / `X-Gc-Commits-After`；
  `POST /maintenance/snapshot` 回 `X-Commit-Id` / `X-Snapshot-Sha256` / `X-Snapshot-Bytes`
  （文件模式另有 `X-Snapshot-Path`）—— **调度侧不该为了取一个数去解 JSON**。

## 8. 失败可见（不静默）

GC 失败时：异常**照抛**（不吞）+ ERROR 日志 + `maintenance.gcFailures` 计数 +1
+ `maintenance.lastError` 记录异常摘要。HTTP 侧返回 4xx/5xx 与错误信息，
**不会**返回"成功但没干活"。

## 9. 快照（同一批运维面）

`POST /maintenance/snapshot?branch=main&dir=...`（`stream=true` 时二进制回传，
元数据在 `X-Commit-Id` / `X-Snapshot-Sha256` 响应头）——
导出的是**该分支 head 的完整视图**（`exportSnapshot` = `GraphDelta.between(空视图, head 视图)`，
节点/边 id 原样保留），因此回读时 `importSnapshot` 能还原出**同样的 id 与属性**。
备份链（滚动保留 N 份 + 归档 z-oss）见 z-oss 仓 `_doc/002_ops/01_备份链与滚动保留.md`。
